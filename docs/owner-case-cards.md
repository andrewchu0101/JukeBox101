# Owner 待審案件卡片

狀態：本機開發完成、已通過離線與可丟棄 PostgreSQL 測試；**尚未部署、尚未同步到 Discord、尚未在真實 Discord 驗收**。

## 為什麼做

Owner 以前要先 `/owner list` 看編號、複製 operation ID、再逐一輸入 `/owner approve …`。卡片讓 Owner 在 Discord 內一鍵處理，不必查資料庫、撈案件編號或操作 VPS。

## 使用方式

1. 在 Owner 伺服器輸入 `/owner list`（無參數）。系統以**只有自己看得到**的訊息顯示最早的一筆待處理案件。
2. 卡片顯示：投稿者、影片連結、已知時長、審核狀態、版本狀態、待處理原因，以及一行提醒「確認通過只核准歌曲資格，不代表錄音版本已確認，也不保證發獎」。
3. 按下方按鈕：

| 按鈕 | 作用 | 何時可按 |
| --- | --- | --- |
| 確認通過 | 核准**歌曲資格**，按下即執行（卡片本身就是預覽，不再多一次確認） | 審核狀態為「待審核」 |
| 拒絕 | 開啟簡單表單填理由，送出即執行 | 待驗證、待審核、驗證失敗 |
| 補時長 | 開啟表單填秒數與來源，送出即執行 | 只在**沒有可信時長**時出現 |
| 下一筆 | 只切換顯示下一筆，不改任何案件或受理順序 | 一律可按 |
| 重新載入 | 重新讀取目前最早的待處理案件 | 卡片過期、已處理或沒有更多時出現 |

4. 版本未確認的案件，另有版本按鈕（確認為新的錄音版本、確認為同一錄音 N、更多已知版本、其他情況…），見下方〈版本確認〉。
5. 操作後，這張卡片會被換成**實際結果**：已確認的審核狀態與修訂、以及獎勵／版本狀態（待版本、待前序、已發 +1、結果未知）。這些文字來自既有服務的結算說明，卡片不自己判斷是否發獎。

案件編號（operation ID）不會出現在卡片，也不會出現在按鈕 ID 中。

## 安全與一致性

- **Owner／伺服器檢查**：每次按鈕與表單送出都先通過 `OwnerGate`（與既有指令同一套），非 Owner 或非指定伺服器只收到統一的拒絕訊息，且不會讀取或寫入任何資料。
- **按鈕只決定它顯示的那一版**：按鈕 ID 形如 `ocard:<動作>:<受理順序>:<顯示的修訂>`。按下時重新讀取該案件，若修訂已變、案件已不在待處理清單，只回覆「卡片已失效，沒有執行任何操作」並提供「重新載入」，**不寫入任何資料**。
- **兩層防護**：卡片層先比對修訂；真正寫入時，既有 `OwnerReviewService.preview` 仍以同一個修訂做 expected-revision 檢查，過期會被服務拒絕。
- **雙擊與並行**：同一個案件的按鈕在記憶體內序列化；第二次按下時案件已變，視為過期，**不會重複決定、也不會重複結算**。
- **結果未知**：若確認時連線中斷（`ReviewOutcomeUnknown`），卡片保留同一個預覽憑證，Owner 再按同一個按鈕時以**同一憑證**重試，不會產生第二個決定。
- **重啟**：按鈕以 discord.py 的 `DynamicItem` 註冊，舊訊息上的按鈕在重啟後仍會被辨識，並用上述修訂檢查拒絕過期操作。目前只以離線方式驗證「從按鈕 ID 重建並拒絕過期操作」，**尚未在真實 Discord 與真實重啟驗證**。送出前被重啟中斷的表單無法恢復，Discord 會顯示失敗，Owner 重新 `/owner list` 即可。
- **不另建帳本**：所有決定都走既有的 `preview → confirm` 交易，結算說明也沿用 `settlement_note`；卡片不寫任何自己的資料表。
- **不猜版本**：「確認通過」不呼叫任何版本確認，也不假設是全新錄音；版本仍由 Owner 另外確認。

## 與既有指令的關係

- `/owner show`、`approve`、`reject`、`duration`、`confirm_version`、`reexamine` 全部保留，行為不變。
- `/owner list` 的指令簽名沒有改變，所以 Owner 伺服器的指令 digest 與先前相同（`26a2d814…`，以固定測試值預覽比對）。
- 沒有注入卡片時（例如單元測試）`/owner list` 仍回傳舊的文字列表。正式啟動時由 `JukeBoxClient` 注入卡片。

## 版本確認：只問系統真正缺少的判斷（已實作，本機驗證）

### 系統已知的事，一律沿用，不再問 Owner

| 情況 | 系統怎麼做 | 對 Owner |
| --- | --- | --- |
| **相同 Video ID** 再被投稿 | 沿用既有影片的審核與版本身分，不覆蓋；新增一筆投稿事件但不重算 | 不產生新問題。**同一支影片只會在佇列出現一次**（最早的受理） |
| **不同 Video ID**，且該影片已有 Owner 確認過的版本對應，並與已領獎的版本相同 | 沿用該影片的版本；同一版本只獎勵一次，不重複發獎 | 佇列為空，不重複詢問 |
| **不同 Video ID，系統沒有任何版本對應** | 維持「未確認」。**不會**因為 Video ID 不同就自動建立新版本，也不會自動對應到別的版本 | 這才是系統真正缺少的判斷，才進佇列並出現版本按鈕 |
| 版本證據互相矛盾 | 凍結為「衝突」 | 進佇列，卡片顯示衝突原因；**不提供**版本按鈕（避免覆蓋矛盾的證據） |

「沒有找到版本對應」只代表系統不知道，**不是**「確定是新錄音」。卡片的版本欄寫的是：「未確認（系統沒有這支影片的版本對應；這不代表它是新錄音）」。

### 人工確認遵守既有服務允許的規則（沒有新增門檻）

- 一般官方原版（basic，不宣稱特殊類別）**不需要第三方證據**。服務只要求一個可追溯的來源參考：網址、文件名或人工核對說明，8 到 512 個字元；這只是格式規則，不是可靠度證明。Owner 在預覽後按下確認，就是確認（`owner_confirmed`）。
- 只有 Live、Cover、Remix、重新錄製等特殊類別才要額外的來源證據；MV 與純音源、重製（同一原始演出）依規則視為同一錄音，同樣要有 Owner 確認過的可追溯來源。剪輯、加速、延長依規則不另計獎勵。
- 標題、標籤、頻道、影片 ID 都不算證據；網址只是被審查的來源，本身不證明兩支影片同錄音或不同錄音。
- 資料庫沒有「版本名稱」欄位，標題也因政策不保存。已知版本清單顯示**首位影片連結＋建立日期**；不新增命名動作。

### 卡片上的版本按鈕（版本未確認時才出現）

| 按鈕 | 按一次的效果 | 來源記錄 |
| --- | --- | --- |
| 確認為新的錄音版本 | 為這支影片建立一個**新的版本**。版本編號由系統產生（`rv-` 加隨機值，不由影片 ID 或網址推導），只在 Owner 按下時才建立 | 「人工核對：此影片連結」 |
| 確認為同一錄音 N | 把這支影片記為**所選已知版本**的同一錄音。每個已知版本一列、各有一個按鈕，選取與確認就是這一按。**不宣稱特定類別**（不寫成 MV／Audio） | 「人工核對：兩支影片連結」 |
| 更多已知版本 | 翻到下一頁已知版本（每頁 5 筆），只換顯示，不寫入 | — |
| 其他情況… | 開啟**類別選單**（見下節），選單本身不寫入 | — |

- 兩個確認按鈕都是 basic 版本斷言（不帶類別），因此沿用既有規則，沒有新增必填的第三方證據。
- **卡片本身就是預覽**：卡片下方先寫清楚每個按鈕的承諾，按一次即確認，沒有第二次形式性確認。承諾包括：由 Owner 判斷、來源如何記錄、「是否發獎依既有規則（先投稿者優先、同一版本只獎勵一次，且只有自動發獎開關開啟、其餘資格成立時才結算），結果會在按下後顯示」。
- 全部走既有的 `preview_version_confirmation` → `confirm`，**綁定卡片顯示的修訂**；沿用服務層權限、短效憑證、交易與冪等。確認後依既有開關與資格結算，卡片換成實際結果（例如「已為投稿者發放 +1」或待前序／未開啟發獎）。
- 已知版本清單由唯讀、有界的查詢提供（`list_known_versions`）：每個版本只出現一次，以版本首位影片的受理順序排序與分頁；SQL 端 `LIMIT 筆數+1`，傳回列數 ≤ 頁大小 + 1。按鈕只攜帶這個受理順序，不攜帶內部版本編號。

### 例子 1：系統沒有版本對應的官方原版（Owner 按 1 次）

```
待處理案件
投稿者：<@…>
影片：https://www.youtube.com/watch?v=AAA…
已知時長：3:09（189 秒）
審核狀態：已核准
版本狀態：未確認（系統沒有這支影片的版本對應；這不代表它是新錄音）
待處理：歌曲已核准，版本待 Owner 判斷

已知版本：無

• 「確認為新的錄音版本」表示由你判斷：這支影片是一個獨立的錄音版本。來源記為「人工核對：此影片連結」。
• 「確認為同一錄音」表示你已比對兩支影片，判斷是同一個錄音；不宣稱特定類別（MV、純音源、重製等），來源記為兩支影片連結。
• 是否發獎依既有規則：先投稿者優先、同一版本只獎勵一次，且只有自動發獎開關開啟、其餘資格成立時才結算。結果會在按下後顯示。
[確認通過(灰)] [拒絕(灰)] [下一筆]
[確認為新的錄音版本] [其他情況…]
```

- **Owner 要看**：影片連結，判斷是不是這首歌的官方原版。
- **按幾次**：1 次，不輸入任何文字。若歌曲資格還在待審核（未被信任的頻道），先按「確認通過」再按「確認為新的錄音版本」，共 2 次，因為是兩個不同的承諾。
- **實際承諾**：只承諾「記錄這個版本」；發不發 Nickel 由既有規則決定。

### 例子 2：已存在 MV，現在投稿的是 Audio（Owner 按 1 次）

```
待處理案件
…（同上，影片：https://www.youtube.com/watch?v=BBB…）
版本狀態：未確認（系統沒有這支影片的版本對應；這不代表它是新錄音）

已知版本（點連結比對）：
 1. 首位影片 https://www.youtube.com/watch?v=MMM…（2026-10-20 建立）
 2. 首位影片 https://www.youtube.com/watch?v=CCC…（2026-10-25 建立）
[確認通過(灰)] [拒絕(灰)] [下一筆]
[確認為新的錄音版本] [其他情況…]
[確認為同一錄音 1] [確認為同一錄音 2]
```

- **Owner 要看**：把投稿影片與清單中每個已知版本的首位影片對照，判斷是不是同一個錄音。
- **按幾次**：1 次，在對的那一列按「確認為同一錄音 N」。
- **實際承諾**：這支影片的版本 = 所選版本。不會僅因 Video ID 不同就當成新版本；該版本若已領過首次獎勵，不重複發放。

### 「其他情況…」類別表單（已實作，本機驗證）

按「其他情況…」後，卡片換成類別選單，並顯示操作承諾：

| 按鈕 | 效果 | 使用的既有類別 |
| --- | --- | --- |
| Live 現場、Cover 翻唱、Remix、重新錄製 | 為這支影片建立**新的版本**（隨機 `rv-` 編號），並把所選類別記在證據上 | `LIVE`、`COVER`、`REMIX`、`RE_RECORDING` |
| 重製：同一錄音 N | 對應到清單中的某個已知版本，視為同一錄音（每個已知版本一個按鈕，可翻頁） | `REMASTER` |
| 返回 | 回到卡片，不寫入 | — |

- 每個選項都會開啟一個表單，只有一個必填欄位：**判斷依據（可追溯的連結或說明）**。表單自動綁定目前案件與卡片顯示的修訂，**不要求案件編號或內部版本編號**。
- **來源必須由 Owner 輸入，系統不自動帶入影片連結**（不像「新版本」「同一錄音」的 basic 按鈕）。送出時先用與 `/owner confirm_version` **同一個** `require_traceable_source` 檢查（8 到 512 個字元、不能是純數字或互動編號），不符合就不呼叫服務、不建立任何版本，案件維持待處理，並說明原因。這沒有新增門檻，也沒有降低。
- 通過格式檢查後，沿用既有的 `preview_version_confirmation` → `confirm`，綁定顯示的修訂。若既有規則判定證據不足（服務拋出 `evidence establishes no recording version`），不發出憑證、不寫入，卡片回到原狀並顯示「證據不足…維持待處理」。
- 確認後依既有開關與資格結算，卡片換成實際結果（類別會寫在結果上）；雙擊、過期、重啟、未知結果的保護與其他按鈕相同。
- **誠實的限制**：程式只能檢查來源的「格式」與 Owner 的確認，無法判斷來源內容是否真的是「獨立的演出證據」；這一項依然是 Owner 的判斷，與 `/owner confirm_version` 完全相同。

剪輯、加速、延長依既有規則不另計獎勵，沿用 `/owner confirm_version`，沒有新增按鈕。

## 已知限制

- **補時長已綁定顯示的修訂**：卡片把顯示的修訂傳給 `OwnerReviewService.preview_duration(expected_revision=…)`，預覽與交易內的確認都以它核對；比對後才被改動的案件會被服務拒絕。
- **待處理查詢有界**：`/owner list` 與「下一筆」使用 `pending_review_page`，SQL 端以條件、排序與 `LIMIT 筆數+1` 限制傳輸量（回傳列數 ≤ 頁大小 + 1），Python 端再套同一條件。資料庫仍可能為了找到第一筆待處理案件而掃描較舊的已完成事件；若案件量很大，可加一個部分索引，但那需要 migration，尚未做也尚未核准。
- 記憶體鎖只是減少重複工作的禮貌性機制，不是正確性的依據。即使兩個互不共用鎖的處理器（或重啟後的新處理器）同時按同一個按鈕，真正的把關是資料庫交易內的修訂核對；PG 測試已驗證只會產生一筆決定、一筆獎勵。
- 卡片文字使用 `<@使用者ID>` 顯示投稿者，訊息設為不提及任何人，不會通知投稿者。
- 重啟時，送出前被中斷的表單無法恢復；服務的預覽憑證也只存在記憶體，重啟後遺失。此時再按舊按鈕，會重新預覽：若先前的決定其實已寫入，修訂已前進，卡片會顯示過期而不會再寫一次。
