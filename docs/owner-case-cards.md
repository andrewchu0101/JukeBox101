# Owner 待審案件卡片

狀態：本機開發完成、已通過離線與可丟棄 PostgreSQL 測試；**尚未部署、尚未同步到 Discord、尚未在真實 Discord 驗收**。

## 為什麼做

Owner 以前要先 `/owner list` 看編號、複製 operation ID、再逐一輸入 `/owner approve …`。卡片讓 Owner 在 Discord 內一鍵處理，不必查資料庫、撈案件編號或操作 VPS。

## 使用方式

1. 在 Owner 伺服器輸入 `/owner list`（無參數）。系統以**只有自己看得到**的訊息顯示最早的一筆待處理案件。
2. 卡片顯示：投稿者、影片連結、已知時長、審核狀態、版本狀態、待處理原因，以及一行提醒「確認通過只核准歌曲資格，不代表錄音版本已確認，也不保證發獎」。
3. 按下方按鈕：

| 按鈕 | 作用 | 何時可按 |
| --- | --- | --- |
| 確認通過 | 核准**歌曲資格**，按下即執行（卡片本身就是預覽，不再多一次確認） | 審核狀態為「待審核」 |
| 拒絕 | 開啟簡單表單填理由，送出即執行 | 待驗證、待審核、驗證失敗 |
| 補時長 | 開啟表單填秒數與來源，送出即執行 | 只在**沒有可信時長**時出現 |
| 下一筆 | 只切換顯示下一筆，不改任何案件或受理順序 | 一律可按 |
| 重新載入 | 重新讀取目前最早的待處理案件 | 卡片過期、已處理或沒有更多時出現 |

4. 操作後，這張卡片會被換成**實際結果**：已確認的審核狀態與修訂、以及獎勵／版本狀態（待版本、待前序、已發 +1、結果未知）。這些文字來自既有服務的結算說明，卡片不自己判斷是否發獎。

案件編號（operation ID）不會出現在卡片，也不會出現在按鈕 ID 中。

## 安全與一致性

- **Owner／伺服器檢查**：每次按鈕與表單送出都先通過 `OwnerGate`（與既有指令同一套），非 Owner 或非指定伺服器只收到統一的拒絕訊息，且不會讀取或寫入任何資料。
- **按鈕只決定它顯示的那一版**：按鈕 ID 形如 `ocard:<動作>:<受理順序>:<顯示的修訂>`。按下時重新讀取該案件，若修訂已變、案件已不在待處理清單，只回覆「卡片已失效，沒有執行任何操作」並提供「重新載入」，**不寫入任何資料**。
- **兩層防護**：卡片層先比對修訂；真正寫入時，既有 `OwnerReviewService.preview` 仍以同一個修訂做 expected-revision 檢查，過期會被服務拒絕。
- **雙擊與並行**：同一個案件的按鈕在記憶體內序列化；第二次按下時案件已變，視為過期，**不會重複決定、也不會重複結算**。
- **結果未知**：若確認時連線中斷（`ReviewOutcomeUnknown`），卡片保留同一個預覽憑證，Owner 再按同一個按鈕時以**同一憑證**重試，不會產生第二個決定。
- **重啟**：按鈕以 discord.py 的 `DynamicItem` 註冊，舊訊息上的按鈕在重啟後仍會被辨識，並用上述修訂檢查拒絕過期操作。目前只以離線方式驗證「從按鈕 ID 重建並拒絕過期操作」，**尚未在真實 Discord 與真實重啟驗證**。送出前被重啟中斷的表單無法恢復，Discord 會顯示失敗，Owner 重新 `/owner list` 即可。
- **不另建帳本**：所有決定都走既有的 `preview → confirm` 交易，結算說明也沿用 `settlement_note`；卡片不寫任何自己的資料表。
- **不猜版本**：「確認通過」不呼叫任何版本確認，也不假設是全新錄音；版本仍由 Owner 另外確認。

## 與既有指令的關係

- `/owner show`、`approve`、`reject`、`duration`、`confirm_version`、`reexamine` 全部保留，行為不變。
- `/owner list` 的指令簽名沒有改變，所以 Owner 伺服器的指令 digest 與先前相同（`26a2d814…`，以固定測試值預覽比對）。
- 沒有注入卡片時（例如單元測試）`/owner list` 仍回傳舊的文字列表。正式啟動時由 `JukeBoxClient` 注入卡片。

## 版本確認：最少操作草案（尚未實作；等 Owner 確認下列語意後才實作）

### 先核對：既有規則允許什麼（已讀程式）

- **一般官方原版（basic，不宣稱特殊類別）不需要第三方證據**。服務只要求一個「可追溯的來源參考」：網址、文件名或人工核對說明，8 到 512 個字元，不能是純數字或互動編號；這只是來源格式規則，**不是可靠度證明**。Owner 在正式預覽後按下確認，就是確認（`owner_confirmed`）。
- 只有 Live、Cover、Remix、重新錄製等**特殊類別**才需要獨立的演出或來源證據；MV 與純音源、重製（同一原始演出）依規則視為「同一錄音」，同樣要有 Owner 確認過的可追溯來源。剪輯、加速、延長依規則不另計獎勵。
- 標題、標籤、頻道、影片 ID 都不算證據；網址只是被審查的來源，不會自動證明兩支影片同錄音或不同錄音。
- **資料庫目前沒有「版本名稱」欄位**：`jb2_versions` 只有版本編號、證據參考與建立時間，`/owner confirm_version` 的 `version_name` 就是版本編號本身。標題因政策不保存。所以「易辨識名稱」只有兩種來源：Owner 選填的名稱，或沒有名稱時顯示**首位影片連結＋建立日期**。

### 設計原則

- Owner 不輸入內部編號；版本編號由系統產生（隨機，不由影片 ID 或網址推導），綁在該次決定的憑證上，重送時不變。
- **卡片本身就是預覽**，在卡片上先把承諾寫清楚，按一次就執行，不再加第二次確認。
- 歌曲通過與版本確認仍是兩個獨立的承諾，兩次按鍵，不合併。
- 不新增產品規則，也不降低證據要求。

### 例子 1：首次官方原版（最常見，按 1 次）

情境：可信頻道的官方影片，系統已自動審核通過；目前沒有任何已知版本。

```
待確認錄音版本
投稿者：<@…>    影片：https://youtu.be/AAA…    時長：3:09
歌曲資格：已核准（自動審核）    版本狀態：未確認

已知版本：無

按下「確認為新的錄音版本」即表示：
 • 此影片記為一個新的錄音版本，來源記為「人工核對：此影片連結」。
 • 是否發獎依既有規則：先投稿者優先、同一版本只獎勵一次，
   且只有在自動發獎開關開啟、其餘資格成立時才結算。結果會在按下後顯示。
[ 確認為新的錄音版本 ]  [ 其他情況… ]  [ 下一筆 ]
```

- **Owner 要看**：影片連結（點開確認是官方原版）、「已知版本：無」。
- **按幾次**：1 次，不需輸入任何文字。
- **實際承諾**：只承諾「建立版本並記錄」；發不發 Nickel 由既有規則決定並在結果卡片顯示（例如「已發放 +1」或「待前序／未開啟發獎」）。
- 若影片來自**未被信任的頻道**（歌曲資格還在待審核），需要先按「確認通過」，再按「確認為新的錄音版本」，共 **2 次**，因為是兩個不同的承諾。

### 例子 2：已存在 MV，現在投稿的是 Audio（按 1 次）

情境：先前已有一個版本，首位影片是 MV；現在有人投稿同一錄音的純音源影片。

```
待確認錄音版本
投稿者：<@…>    影片：https://youtu.be/BBB…    時長：3:08
歌曲資格：已核准    版本狀態：未確認

已知版本（點連結比對）：
 • 〈晴天 原版〉   首位影片 https://youtu.be/MMM…   2026-10-20 建立    [ 與此版本相同 ]
 • （未命名）      首位影片 https://youtu.be/CCC…   2026-10-25 建立    [ 與此版本相同 ]
                                                              [ 下一頁 ]

按下「與此版本相同」即表示你已比對過兩支影片，確認它們是同一個錄音（MV／純音源）：
 • 此影片併入該版本，來源記為「人工核對：兩支影片連結」，類別為「MV 與純音源同一錄音」。
 • 該版本若已領過首次獎勵，本次不重複發放；其餘依既有規則決定，結果會在按下後顯示。
[ 新的錄音版本 ]  [ 其他情況… ]  [ 下一筆 ]
```

- **Owner 要看**：把投稿影片與清單中每個已知版本的首位影片對照，判斷是不是同一個錄音。
- **按幾次**：1 次（在對的那一列按「與此版本相同」），不輸入文字。
- **實際承諾**：這支影片的錄音版本 = 所選版本，並且不會僅因影片 ID 不同就當成新版本。獎勵結果由既有規則決定。

### 需要額外判斷的案件：「其他情況…」才出現表單

- 只有在 Live、Cover、Remix、重新錄製、重製（同一原始演出）時才打開表單：選類別、**填一個可追溯的來源（必填）**，並選擇它屬於新版本或既有版本。證據要求完全沿用既有規則，不降低；來源不足時沿用既有「證據不足」回覆，案件維持待處理。
- 剪輯、加速、延長沿用既有規則，不新增按鈕；需要時仍用 `/owner confirm_version` 指定該類別。

### 實作需要什麼（不需要 migration）

- 一個**唯讀**查詢：列出已知版本（版本編號、首位影片連結、建立日期、若有 Owner 填的名稱）。資料已在 `jb2_versions`、`jb2_videos`、`jb2_events`，版本在 `identity_json` 內，需要用 JSON 路徑取出，實作時以可丟棄 PostgreSQL 驗證。已知版本多時分頁（每頁 5 筆）。
- 卡片的按鈕沿用現有的 `preview_version_confirmation` → `confirm`，綁定顯示的修訂，與「確認通過」相同的雙擊、過期、重啟保護。

### 需要 Owner 確認的語意

1. **首次官方原版的來源**：按鈕自動把「此影片連結」記為人工核對來源，而不是要求第三方連結。這符合既有 basic 規則，但等於「你的按鍵就是確認」。可以嗎？
2. **MV／純音源同一錄音**：按鈕自動把「兩支影片連結」記為人工核對來源，類別帶入「MV 與純音源同一錄音」。既有規則允許（要求 Owner 確認過、來源可追溯）。可以嗎？還是你希望這類也要多填一個第三方連結？
3. **名稱**：因為系統不保存標題，已知版本清單只能顯示 Owner 選填的名稱，或沒名稱時顯示首位影片連結＋建立日期。你要在建立版本後提供一個選填的「命名」動作嗎？還是只用連結就夠？
4. **未被信任頻道的案件需要 2 次按鍵**（通過＋版本）。是否接受？我建議接受，因為這兩個承諾不同，合併會讓 Owner 默默承諾第二件事。
5. **獎勵承諾的措辭**：卡片按下前只說「依既有規則決定，結果按下後顯示」，不預先宣稱會不會發。這樣的措辭可以嗎？

## 已知限制

- **補時長已綁定顯示的修訂**：卡片把顯示的修訂傳給 `OwnerReviewService.preview_duration(expected_revision=…)`，預覽與交易內的確認都以它核對；比對後才被改動的案件會被服務拒絕。
- **待處理查詢有界**：`/owner list` 與「下一筆」使用 `pending_review_page`，SQL 端以條件、排序與 `LIMIT 筆數+1` 限制傳輸量（回傳列數 ≤ 頁大小 + 1），Python 端再套同一條件。資料庫仍可能為了找到第一筆待處理案件而掃描較舊的已完成事件；若案件量很大，可加一個部分索引，但那需要 migration，尚未做也尚未核准。
- 記憶體鎖只是減少重複工作的禮貌性機制，不是正確性的依據。即使兩個互不共用鎖的處理器（或重啟後的新處理器）同時按同一個按鈕，真正的把關是資料庫交易內的修訂核對；PG 測試已驗證只會產生一筆決定、一筆獎勵。
- 卡片文字使用 `<@使用者ID>` 顯示投稿者，訊息設為不提及任何人，不會通知投稿者。
- 重啟時，送出前被中斷的表單無法恢復；服務的預覽憑證也只存在記憶體，重啟後遺失。此時再按舊按鈕，會重新預覽：若先前的決定其實已寫入，修訂已前進，卡片會顯示過期而不會再寫一次。
