# Owner 待審案件卡片

狀態：本機開發完成、已通過離線與可丟棄 PostgreSQL 測試；**尚未部署、尚未同步到 Discord、尚未在真實 Discord 驗收**。

## 為什麼做

Owner 以前要先 `/owner list` 看編號、複製 operation ID、再逐一輸入 `/owner approve …`。卡片讓 Owner 在 Discord 內一鍵處理，不必查資料庫、撈案件編號或操作 VPS。

## 使用方式

1. 在 Owner 伺服器輸入 `/owner list`（無參數）。系統以**只有自己看得到**的訊息顯示最早的一筆待處理案件。
2. 卡片顯示：投稿者、影片連結、已知時長、審核狀態、版本狀態、待處理原因，以及一行提醒「確認通過只核准歌曲資格，不代表錄音版本已確認，也不保證發獎」。
3. 按下方按鈕：

| 按鈕 | 作用 | 何時可按 |
| --- | --- | --- |
| 確認通過 | 核准**歌曲資格**，按下即執行（卡片本身就是預覽，不再多一次確認） | 審核狀態為「待審核」 |
| 拒絕 | 開啟簡單表單填理由，送出即執行 | 待驗證、待審核、驗證失敗 |
| 補時長 | 開啟表單填秒數與來源，送出即執行 | 只在**沒有可信時長**時出現 |
| 下一筆 | 只切換顯示下一筆，不改任何案件或受理順序 | 一律可按 |
| 重新載入 | 重新讀取目前最早的待處理案件 | 卡片過期、已處理或沒有更多時出現 |

4. 操作後，這張卡片會被換成**實際結果**：已確認的審核狀態與修訂、以及獎勵／版本狀態（待版本、待前序、已發 +1、結果未知）。這些文字來自既有服務的結算說明，卡片不自己判斷是否發獎。

案件編號（operation ID）不會出現在卡片，也不會出現在按鈕 ID 中。

## 安全與一致性

- **Owner／伺服器檢查**：每次按鈕與表單送出都先通過 `OwnerGate`（與既有指令同一套），非 Owner 或非指定伺服器只收到統一的拒絕訊息，且不會讀取或寫入任何資料。
- **按鈕只決定它顯示的那一版**：按鈕 ID 形如 `ocard:<動作>:<受理順序>:<顯示的修訂>`。按下時重新讀取該案件，若修訂已變、案件已不在待處理清單，只回覆「卡片已失效，沒有執行任何操作」並提供「重新載入」，**不寫入任何資料**。
- **兩層防護**：卡片層先比對修訂；真正寫入時，既有 `OwnerReviewService.preview` 仍以同一個修訂做 expected-revision 檢查，過期會被服務拒絕。
- **雙擊與並行**：同一個案件的按鈕在記憶體內序列化；第二次按下時案件已變，視為過期，**不會重複決定、也不會重複結算**。
- **結果未知**：若確認時連線中斷（`ReviewOutcomeUnknown`），卡片保留同一個預覽憑證，Owner 再按同一個按鈕時以**同一憑證**重試，不會產生第二個決定。
- **重啟**：按鈕以 discord.py 的 `DynamicItem` 註冊，舊訊息上的按鈕在重啟後仍會被辨識，並用上述修訂檢查拒絕過期操作。目前只以離線方式驗證「從按鈕 ID 重建並拒絕過期操作」，**尚未在真實 Discord 與真實重啟驗證**。送出前被重啟中斷的表單無法恢復，Discord 會顯示失敗，Owner 重新 `/owner list` 即可。
- **不另建帳本**：所有決定都走既有的 `preview → confirm` 交易，結算說明也沿用 `settlement_note`；卡片不寫任何自己的資料表。
- **不猜版本**：「確認通過」不呼叫任何版本確認，也不假設是全新錄音；版本仍由 Owner 另外確認。

## 與既有指令的關係

- `/owner show`、`approve`、`reject`、`duration`、`confirm_version`、`reexamine` 全部保留，行為不變。
- `/owner list` 的指令簽名沒有改變，所以 Owner 伺服器的指令 digest 與先前相同（`26a2d814…`，以固定測試值預覽比對）。
- 沒有注入卡片時（例如單元測試）`/owner list` 仍回傳舊的文字列表。正式啟動時由 `JukeBoxClient` 注入卡片。

## 版本確認：最少操作草案（尚未實作，需 Owner 決定語意）

卡片目前遇到「歌曲已核准、版本未確認」只顯示原因，並提示用 `/owner confirm_version`。目標是 Owner 不必填內部 version ID。草案：

- 在這類卡片新增「確認版本」按鈕，開啟表單：**來源連結**（可追溯，例如官方專輯頁）與**版本名稱**（例如「原版」「Live」）。系統自動產生內部版本編號，沿用既有 `preview_version_confirmation` 與證據規則。
- 若同一首歌已有已知版本，改以選單選「與哪一筆已知版本相同」，選單文字用影片連結，而不是內部編號。

**需要 Owner 回答才能實作的問題**

1. 「新錄音版本」的內部編號要怎麼產生？以第一支影片為準，之後 MV 與 Audio 再逐一指向它，是否可以？
2. 來源連結可否就是影片本身的網址？還是必須另有第三方證據？
3. Live、Remix、Cover 等類別是否要在這個表單選擇，還是先一律當作基本版本？
4. 確認版本後，是否沿用現有行為：立即自動結算並在卡片顯示結果？

## 已知限制

- **補時長已綁定顯示的修訂**：卡片把顯示的修訂傳給 `OwnerReviewService.preview_duration(expected_revision=…)`，預覽與交易內的確認都以它核對；比對後才被改動的案件會被服務拒絕。
- **待處理查詢有界**：`/owner list` 與「下一筆」使用 `pending_review_page`，SQL 端以條件、排序與 `LIMIT 筆數+1` 限制傳輸量（回傳列數 ≤ 頁大小 + 1），Python 端再套同一條件。資料庫仍可能為了找到第一筆待處理案件而掃描較舊的已完成事件；若案件量很大，可加一個部分索引，但那需要 migration，尚未做也尚未核准。
- 記憶體鎖只是減少重複工作的禮貌性機制，不是正確性的依據。即使兩個互不共用鎖的處理器（或重啟後的新處理器）同時按同一個按鈕，真正的把關是資料庫交易內的修訂核對；PG 測試已驗證只會產生一筆決定、一筆獎勵。
- 卡片文字使用 `<@使用者ID>` 顯示投稿者，訊息設為不提及任何人，不會通知投稿者。
- 重啟時，送出前被中斷的表單無法恢復；服務的預覽憑證也只存在記憶體，重啟後遺失。此時再按舊按鈕，會重新預覽：若先前的決定其實已寫入，修訂已前進，卡片會顯示過期而不會再寫一次。
