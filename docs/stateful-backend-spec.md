# 業務狀態持久化與容器可替換：規格補充

- 日期：2026-10-28
- 狀態：盤點完成；最小修改與驗證尚未實作。
- 關聯：[Docker Gateway 部署規格](docker-deployment-spec.md)、[Nickel 額度規格草案](nickel-grant-spec.md)、[工作票索引](tickets/docker-gateway-deployment/README.md)

## 1. 核心結論

- **容器可以重啟，業務正確性不依賴容器或程序記憶體。** 所有會影響餘額、發放、扣款、退款與派送的狀態，必須以資料庫交易、唯一約束與併發控制保存。
- **本次只支援單一 Gateway 副本。** 業務狀態可持久化，不代表可以任意增加副本；多副本的 Gateway 協調與 sharding 未驗證，部署時一律只跑一個實例。
- **不得以「容器可以重啟」宣稱無狀態。** 無狀態的判斷必須以本文件的盤點與測試為準。

## 3. 必須持久化的業務狀態（驗收）

- 使用者 Nickel 餘額與帳本（S1、S2）。
- 新人額度與定期額度的領取紀錄（規格草案 Nickel 額度；尚未實作，實作時必須以資料庫唯一約束保存）。
- 投稿、審核、版本與獎勵歸屬（S3）。
- 交換、扣款、退款與派送進度（S4、S5）。
- 防重複請求與提交結果不明的恢復依據（唯一鍵、冪等鍵與租約，存於資料庫）。

**禁止**：僅靠記憶體集合、程序內鎖或本機檔案防止重複發放。

## 4. 暫時狀態的處理

- Gateway 連線、連線池與 Discord 快取可留在記憶體，重啟後重建。
- Owner 預覽與確認（S6、S7、S8）：
  - **決定：重啟後安全失效。** 權杖與視窗狀態不持久化；確認時若找不到權杖或權杖已過期，回覆明確的失效訊息，不寫入任何資料。
  - 重啟後的確認不得被誤執行，也不得重複執行。
  - 不得在狀態遺失後錯誤宣稱操作完成。
  - 結果不明的情況（S8）：重啟後若使用者重新預覽，系統必須以資料庫中的案件狀態與修訂號判斷，不得回報舊的「已完成」或誤導性的「已失敗」。**待驗證**，見工作票。
- 暫存檔可丟棄；秘密檔案只讀，不作為業務資料。

## 5. 重啟與故障驗證（隔離測試）

必須用隔離的資料庫驗證，不連線正式 Discord 或正式 MySQL：

1. 已完成的發幣或獎勵重啟後不重發。
2. 同一領取週期重啟後不能重領（待 Nickel 額度實作後驗證）。
3. 已扣款或結果不明的交換，重啟後可辨識，並依既有租約與恢復流程安全處理，不重複扣款。
4. 過期或失效的 Owner 確認操作重啟後不執行。
5. 整個流程不依賴前一程序的記憶體或可寫容器層（以新程序重新建立服務物件後驗證）。

**隔離資料庫的前提**：本機隔離 MySQL 需要使用者授權與既有的隔離設定（見既有測試基礎設施）。在未取得授權前，這些測試標為「待驗證」，不得以離線替身取代後宣稱通過。

## 6. Gateway 部署限制

- 支援的副本數：**1**。
- 背景工作協調：本次未設計；單一副本下不需要分散式協調。
- Gateway／sharding：未驗證多連線的行為，不支援。
- 容器重啟後，業務狀態由資料庫保證；但 Discord 連線與 Owner 視窗需要使用者重新操作。
- 若日後要支援多副本，需另立規格，處理 Gateway 事件重複、背景工作協調與 sharding。

## 7. 本次不做的事

- 不改寫 Owner 審核的整體架構。
- 不把 Owner 預覽權杖改為持久化（改用安全失效）；若 Owner 日後要求持久化，另案處理。
- 不新增人工調帳或補發。
- 不修改既有結算規則。

## 8. 待 Owner 決定

- 是否授權本機隔離 MySQL（容器或本機）執行重啟與並行驗證，且不連線正式資料庫。
- 結果不明的 Owner 操作，重啟後是否需要額外的人工查核提示（目前建議：是，以 `/owner show` 查詢）。
