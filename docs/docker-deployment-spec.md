# JukeBox101 Docker Compose 部署規格（Gateway-only）

- 日期：2026-10-28
- 狀態：規格草案，尚未開始程式實作。
- 需求來源：[需求輸入檔](docker-deployment-requirements-input.md)
- 工作票：待手動執行 `/to-tickets` 後產生。
- 問題追蹤器：專案尚未設定 issue tracker（需先執行 `/setup-matt-pocock-skills`），本規格暫存於專案 `docs/`，未發布到 tracker。

## Problem Statement

JukeBox101 目前只能在開發者的 Windows／WSL 環境中以離線方式驗證。夥伴需要在自己管理的 Linux amd64 主機上，以 Docker Compose 部署同一個 Bot。部署必須：

- 只用精簡交付包與 Docker，不需要原始 Git 歷史或開發工具。
- 不讓任何真實秘密（資料庫密碼、Discord Token）進入交付包、映像或 Compose 檔。
- 讓 Owner 能在夥伴主機上一次性配置秘密，之後更新程式時不需重新提供。
- 讓 Owner 指令在正式入口真正可用，且只限私人伺服器中的 Owner。
- 讓開發者能安全地查看資料庫，而不直接暴露 MySQL 3306。
- 在缺少秘密或設定錯誤時安全停止，不能讓「容器已建立」被誤認為「Bot 已可用」。

## Solution

以 Docker Compose 部署 Gateway-only 的 Bot：Bot 主動連線 Discord，不開放公開 HTTP 入口，也不要求反向代理、網域或 HTTPS。

- 夥伴：在自己的主機上準備 Docker，取得精簡交付包，依「夥伴部署與更新」文件部署與更新。
- Owner：建立資料庫帳號與秘密，透過獨立安全管道配置到夥伴主機，依「Owner 秘密配置與輪替」文件維護。
- 程式：新增明確的秘密檔案讀取，並修正正式入口，使 Owner 指令在 Gateway 中接線。
- 資料庫：預設使用外部 MySQL；另提供選用的同機 Compose profile，3306 不對公網開放。

## Current Feature Status

本節是規格的必要盤點。「已開放」指正式入口目前可對使用者提供；「離線已實作」指程式與離線測試存在，但未通過真實 Discord 或 MySQL 驗收。

| 功能 | 使用者入口 | 目前狀態 | 真實驗收 | 備註 |
|---|---|---|---|---|
| 投稿 YouTube 影片 `/share` | 使用者 | 已開放（僅 YouTube） | 未通過 | Spotify 網址目前被拒絕（與原 MVP 文件的 Spotify 要求不一致，待 Owner 決定） |
| 查詢 Nickel 餘額 `/balance` | 使用者 | 已開放 | 未通過 | 讀取餘額快取，需與帳本一致（見第 4 項需求） |
| 查詢本人投稿與審核狀態 `/history` | 使用者 | 已開放 | 未通過 | 顯示本人投稿與目前狀態 |
| 每日推薦偏好 `/daily` | 使用者 | 只保存偏好，不發送 DM | 未通過 | 回覆「每日排程尚未啟用」 |
| 每日自動 DM 派送 | 使用者 | 未開放 | 未通過 | 排程尚未實作 |
| 正式交換 `/exchange` | 使用者 | 預設關閉（`JUKEBOX_FORMAL_EXCHANGE` 未設定時回覆固定文字） | 未通過 | 真實 MySQL 原子扣點與 DM 派送尚未驗收；本次部署不開啟 |
| Owner 審核 `/owner`（list、show、approve、reject、confirm_version、reexamine） | Owner（私人伺服器限定） | 離線已實作；正式入口未接線 | 未通過 | 見第 2 項需求 |
| Owner 命令列工具（duration、approve、version、settle） | Owner（本機） | 離線已實作 | 未通過 | 寫入前需 digest 與 revision 檢查，不屬於 Discord 功能 |
| 真實 Discord 指令同步 | 開發者 | 未執行 | 未通過 | 本次規格不要求同步；需另行授權 |

**本次部署範圍**：只承諾「已開放」的使用者功能；`/owner` 在接線與驗證完成後納入；`/exchange` 與每日 DM 不開放。

## User Stories

### 夥伴（部署者）

1. 作為夥伴，我想取得精簡交付包，以便在自己的主機上部署，而不需要取得原始 Git 歷史。
2. 作為夥伴，我想依文件安裝 Docker 與 Compose，以便先完成主機準備，再由 Owner 配置秘密。
3. 作為夥伴，我想用一組固定指令建置映像，以便重現相同的部署結果。
4. 作為夥伴，我想在秘密尚未配置時看到明確的停止訊息，以便知道是等待 Owner 而不是程式壞掉。
5. 作為夥伴，我想知道容器存活、設定載入與 Discord 連線三個階段的狀態，以便判斷 Bot 是否真的可用。
6. 作為夥伴，我想依文件查看日誌，以便回報問題而不需要看到任何秘密。
7. 作為夥伴，我想依文件停止服務，以便進行維護。
8. 作為夥伴，我想在程式更新時沿用既有秘密，以便不需要 Owner 重新提供。
9. 作為夥伴，我想依文件回滾到上一版映像，以便在更新失敗時恢復服務。
10. 作為夥伴，我想知道備份責任人與備份範圍，以便清楚哪些資料需要我或 Owner 保存。
11. 作為夥伴，我想知道健康檢查實際驗證了什麼，以便不誤把「容器健康」當成「Discord 已連線」。
12. 作為夥伴，我想在主機上看到 Compose 的 CPU 與記憶體限制已生效，以便確認資源設定正確。

### Owner（擁有者）

13. 作為 Owner，我想在夥伴主機上一次性配置資料庫密碼與 Discord Token，以便 Bot 能啟動。
14. 作為 Owner，我想秘密只存在於部署主機上的指定路徑，以便不進入交付包、映像或聊天。
15. 作為 Owner，我想輪替資料庫密碼與 Discord Token，並說明生效方式，以便在洩漏時能及時處理。
16. 作為 Owner，我想為 Bot 建立專用、最小權限的資料庫帳號，以便 Bot 被入侵時的影響有限。
17. 作為 Owner，我想讓 Migration 使用另外管理的帳號，以便 Bot 日常執行時不具備結構變更權限。
18. 作為 Owner，我想在 Discord 中使用 `/owner` 指令，以便審核投稿，且只有我本人在私人伺服器中可用。
19. 作為 Owner，我想其他人使用 `/owner` 時得到相同的拒絕訊息，以便不洩漏權限資訊。
20. 作為 Owner，我想在執行 `/owner` 寫入前看到預覽與確認步驟，以便避免誤操作。
21. 作為 Owner，我想在預覽過期或案件已變更時被拒絕，以便避免用舊資料寫入。
22. 作為 Owner，我想所有 Owner 決定都留下可追溯紀錄，以便日後核對。

### 使用者（Discord 成員）

23. 作為使用者，我想投稿 YouTube 影片，並立即知道是否已收到、是否重複、是否待驗證。
24. 作為使用者，我想投稿 Spotify 網址時被清楚告知目前不支援，以便知道原因。
25. 作為使用者，我想查詢自己的 Nickel 餘額，並看到與帳本一致的數字。
26. 作為使用者，我想查看自己的投稿與審核狀態，以便追蹤進度。
27. 作為使用者，我想設定每日推薦偏好時被告知目前不會發送 DM，以便不誤以為已啟用排程。
28. 作為使用者，我想在 `/exchange` 尚未開放時看到明確說明，且不會被扣點。
29. 作為使用者，我想在系統暫時無法處理時看到通用失敗訊息，以便稍後再試。
30. 作為使用者，我想回覆訊息不含他人的私人資料、內部路徑或 SQL，以便保護隱私。
31. 作為使用者，我想使用指令時不會被 @everyone、@here 或角色提及打擾，以便減少騷擾。

### 開發者（維護者）

32. 作為開發者，我想從本機以唯讀帳號查詢資料庫，以便核對投稿與帳本，而不影響線上資料。
33. 作為開發者，我想區分唯讀查詢、Bot 執行與維護帳號的用途，以便不混用權限。
34. 作為開發者，我想 MySQL 3306 不對公網開放，以便降低資料庫暴露面。
35. 作為開發者，我想不直接修改資料表補發 Nickel，而是經過帳本流程，以便保持餘額與帳本一致。
36. 作為開發者，我想離線測試能在 Python 3.12 上執行，以便與部署環境一致。
37. 作為開發者，我想容器在無網路或假值設定下能啟動並停止，以便在不連線正式服務的情況下驗證。
38. 作為開發者，我想容器收到 SIGTERM 時能完成或安全中止進行中的工作，以便避免資料不一致。
39. 作為開發者，我想映像與交付包經過機敏掃描，以便證明沒有秘密殘留。

### 安全與合規

40. 作為 Owner，我想秘密檔案權限同時符合主機保護與非 root 容器讀取需求，以便容器能讀取但其他使用者不能讀取。
41. 作為 Owner，我想清楚知道 Docker secrets 不保證對主機管理員或完整 Docker 權限持有人保密，以便正確評估風險。
42. 作為 Owner，我想 Discord 權限與 intents 只保留必要項目，以便符合 Developer Policy 的最小權限原則。
43. 作為 Owner，我想 Discord 政策檢查與人工 Portal 項目分開列出，以便完成正式上線前的人工設定。

## Implementation Decisions

### 部署模式與入口

- 部署採 Docker Compose，目標為 Linux amd64 主機，由夥伴管理。
- 部署模式為 Gateway-only。Bot 主動連線 Discord；不開放公開 HTTP Interactions 入口；不要求反向代理、網域或 HTTPS。
- 容器只監聽本機或不監聽任何連接埠（Bot 不需要對外開放連接埠）。
- 既有 HTTP Interactions 程式與安全檢查保留，不刪除、不重構、不靜默停用。
- 既有 `deploy/` 目錄中的 HTTP 文件採「方案 A」：保留，並在檔案開頭標示為「未採用的 HTTP 候選方案」，不搬移、不覆寫。

### 秘密管理

- 秘密種類：資料庫密碼、Discord Bot Token。其他執行所需秘密依規格另列。
- 秘密由 Owner 建立、保管、配置與輪替；交付包、映像、Compose 檔與文件不含真實值。
- 秘密透過 Compose secrets 掛載為檔案。程式必須明確支援從秘密檔案讀取；不依賴 `_FILE` 環境變數自動生效。
- 讀取順序與衝突：
  - 若同時提供環境變數與秘密檔案，程式必須拒絕啟動（避免兩個來源不一致）。
  - 秘密檔案不存在、為空、或含前後空白時，程式必須拒絕啟動，錯誤訊息只列出設定名稱，不輸出值。
- 缺少秘密時安全停止，不使用預設密碼，不以空值啟動。
- 秘密不得注入建置階段：不使用 Dockerfile 的 ARG 或 ENV，不使用 build secrets。
- 秘密不得寫入交付包、映像層、日誌、診斷報告或 Compose 檔。
- 秘密檔案路徑可設定，預設值為專案外的部署目錄；實際路徑在正式部署前由 Owner 確認。

### 秘密檔案權限（需同時驗證）

- 檔案擁有者：由 Owner 指定，建議為部署主機上的專用系統帳號。
- 容器內執行身分：非 root，且與檔案讀取權限匹配。
- 權限規則需在部署文件中寫明並於離線驗證中測試：
  - 檔案權限限制為擁有者可讀寫、其他人不可讀（例如 0400 或 0600）。
  - 容器內的非 root 使用者必須能讀取該檔案；2026-10-29 已核准統一為 0400：擁有者必須是指定的數字 UID（10001），不採用 0440 群組讀取；擁有者與容器使用者不同的情況不被接受。
  - 不得只指定 0600 而未驗證檔案擁有者與容器讀取權限。
- 程式在讀取秘密檔案時應檢查：檔案存在、可讀、非空；若權限過寬（例如其他人可讀），應拒絕啟動或至少記錄警告（待 Owner 決定嚴格程度）。
- 驗證方式：離線測試以模擬的擁有者與權限覆蓋各情境；正式主機上的實際權限需由夥伴依部署文件檢查並記錄。

### 權限邊界聲明（必須寫入文件）

- 夥伴若擁有主機管理員或完整 Docker 權限，技術上可以讀取容器使用的秘密。
- Docker secrets 不保證對主機管理員保密，也不是自動加密保管庫。
- 本規格不宣稱秘密對夥伴不可見；保護的是交付包、映像、Git 歷史與聊天記錄不含秘密。

### 健康與就緒

- 健康狀態分三層，文件與程式輸出必須分別說明：
  1. 容器存活：程序仍在執行。
  2. 設定載入：秘密與設定通過驗證。
  3. Discord 連線：Gateway 已登入。
- 健康檢查不得反覆呼叫 Discord API。第 3 層的判斷應依 Bot 內部已有的連線狀態，不另發 API 請求。
- 「容器已建立」或「容器存活」不得被宣稱為「Bot 已可用」。

### Owner 指令接線（必須修正）

- 目前發現：正式 Gateway 入口在建立 Discord 用戶端時，沒有傳入 Owner 審核的接線資訊，因此 `/owner` 群組不會註冊。
- 本規格要求：正式入口必須接入 Owner 審核接線，並由 Owner 身分與私人伺服器限制保護。
- 權限驗證：
  - 只允許設定的私人伺服器與 Owner 使用者；其他人得到相同拒絕訊息，不洩漏原因。
  - 寫入前必須有預覽與確認；確認必須是一次性；過期或案件已變更時拒絕。
- 接線範圍：正式入口、設定讀取、Owner 身分與伺服器 ID 的來源，以及離線測試。
- 不在本規格範圍：Owner 指令的實際 Discord 同步與真實寫入。

### 資料庫帳號與存取

- Bot 使用專用、最小權限帳號，只授予應用程式所需的讀寫權限，不具備結構變更權限。
- Migration 使用另外管理的帳號，只在維護時使用，不放入 Bot 容器。
- 不提供資料庫管理員或 root 密碼給部署環境。
- 3306 不對公網開放。同機 MySQL 的 Compose profile 只連接內部網路。

### 開發者唯讀查詢文件（新需求）

文件需區分三類帳號與用途：

| 帳號類型 | 用途 | 權限 | 存取方式 |
|---|---|---|---|
| 唯讀查詢帳號 | 核對投稿、帳本與狀態 | 只有 SELECT；連線以唯讀 session 開啟 | 經 SSH 隧道或主機內部連線，不開放 3306 |
| Bot 執行帳號 | Bot 日常運行 | 應用程式所需讀寫，不含結構變更 | 只由 Bot 容器使用 |
| 維護帳號 | Migration 與結構維護 | 結構變更權限 | 只在維護時由 Owner 使用，不放入 Bot 容器 |

- 文件需說明：如何建立唯讀帳號（由 Owner 執行，不由程式自動建立）、如何經 SSH 隧道查詢、禁止在查詢工具中執行寫入語句。
- 唯讀連線應設定唯讀 session，與既有唯讀檢查的做法一致。

### 帳本與 Nickel 一致性（新需求）

- Nickel 餘額以帳本為準。餘額快取與帳本必須保持一致。
- 任何 Nickel 的增減都必須以「帳本新增一筆紀錄，並在同一交易中更新餘額快取」的方式完成。
- 禁止以直接 UPDATE 資料表的方式補發或扣除 Nickel。
- 目前既有的寫入路徑（投稿獎勵、交換扣點、派送退款、補償）都採用上述成對寫入的模式。
- 本規格新增要求：
  - 不新增任何「手動調整 Nickel」的 Owner 指令，除非另行核准。
  - 補發或扣除必須走已核准的補償流程，且需有帳本理由與冪等鍵。
  - 離線測試需驗證：餘額快取與帳本總和一致；直接改表會被帳本完整性檢查發現。
- 補償流程目前尚未通過真實驗收，不得在正式部署中作為管理手段，直到驗收完成。

### 回覆文案（沿用既有決策）

- 統一使用 Nickel（不使用「點數」作為面向使用者的詞）。
- 既有 5 句逐字核准台詞保持原樣。
- 新文案待 Owner 確認後套用，不阻擋部署與離線工作。

### 容器與資源

- 映像：精簡基底，支援 linux/amd64；非 root 執行；不含測試或編譯工具。
- 依賴鎖定：使用既有版本清單，建置可重現。
- 信號：正確處理 SIGTERM，先停止接收新工作，再於時限內完成或中止進行中工作，然後關閉連線。
- 資源限制：Compose 的 CPU 與記憶體限制必須在選定模式下實際生效；預留空間給作業系統與同機 MySQL（若使用）。
- 日誌：設定輪替與大小上限，避免磁碟耗盡。

### 交付包

- 包含：實際必要程式、Dockerfile、Compose、依賴鎖定、假值設定範例、部署文件、必要 SQL 資源與授權資訊。
- 不包含：`.env`、`.local/`、`.git/`、私人驗收證據、真實憑證、資料庫 dump 或 volume、虛擬環境、快取與日誌。
- 不依賴 `.gitignore`：使用獨立的 Docker 排除規則與交付允許清單。
- 交付後需解壓複查、掃描，並提供 SHA-256。

### Python 版本

- 測試與執行使用 Python 3.12（可用路徑：`<HOME>/.local/bin/python3.12`（`<HOME>` 為本機使用者主目錄的佔位符），版本 3.12.15）。
- `/usr/bin/python3`（3.14.4）不屬於本專案範圍，不得用於驗收。

### 磁碟與環境

- C 槽剩餘約 11 GiB（96% 使用）。建置前需重新確認 Docker Desktop 的儲存位置與可用空間。
- 不執行全域 prune，不清理既有容器、映像、volume、WSL 虛擬磁碟或使用者檔案。

## Testing Decisions

### 測試原則

- 只測試外部行為，不測試內部實作細節。
- 每個測試應讀起來像規格：例如「缺少秘密檔案時 Bot 拒絕啟動」。
- 離線測試不連線正式 Discord 或正式 MySQL。

### 測試的 seams（待確認）

1. **設定與秘密讀取的介面**：輸入為環境與秘密檔案位置，輸出為設定或拒絕啟動。可捕捉：秘密來源衝突、缺少秘密、空值、權限錯誤。不捕捉：Discord 實際登入。
2. **正式 Gateway 入口的客戶端建構**：可在不登入 Discord 的情況下檢查 Owner 指令是否註冊、是否只限指定伺服器。可捕捉：接線遺漏、權限限制錯誤。不捕捉：真實 Discord 指令同步。
3. **容器層級離線驗證**：使用假值與無網路容器，驗證建置、非 root、SIGTERM、資源限制、健康狀態分層。可捕捉：映像與 Compose 問題。不捕捉：Discord 與 MySQL 的真實行為。
4. **帳本與餘額一致性**：以資料庫層的完整性檢查驗證，不直接修改資料表。可捕捉：直接改表造成的不一致。

建議：優先使用第 1 與第 2 點作為主要 seams，它們是最高且最接近行為的介面。需 Owner 確認。

### 必須的測試

- 秘密讀取：來源衝突拒絕、缺少拒絕、空值拒絕、錯誤訊息不含秘密值。
- 秘密權限：模擬擁有者與容器使用者的組合，驗證非 root 能讀取、其他人不能讀取。
- Owner 接線：正式入口註冊 `/owner`；非 Owner 或其他伺服器得到相同拒絕；預覽過期與案件變更時拒絕寫入。
- Nickel 一致性：餘額快取與帳本總和一致；直接改表會被偵測。
- 容器：無秘密啟動時安全停止；SIGTERM 收到後在時限內結束；非 root 執行。
- 交付包：掃描結果不含秘密樣式；解壓後檔案清單符合允許清單。

## 十、2026-10-28 決策更新（雲端部署情境）

- **部署主機**：正式 Bot 部署在雲端 Linux amd64 主機。本機 Docker 僅供開發與驗證，不是正式環境。
- **雲端帳號歸屬、實際主機權限與維護責任**：部署前待確認，不假設主機屬於夥伴，也不假設部署責任等於完整管理權限。
- **分工**：
  - 夥伴：準備部署環境、部署與更新 Docker Compose、檢查運行狀況。
  - Owner：管理 Discord 應用程式、建立與輪替秘密、核准正式資料庫變更。
  - 備份、還原與主機日常維護責任人：部署前另行確認。
- **外部 MySQL**：預設使用外部 MySQL。位置與安全連線方式（TLS、網路限制）須明確記錄；不假設使用 Owner 的本機資料庫；不直接公開 3306。同機 MySQL profile 維持為選用。
- **秘密權限預期值**：以 `SECRET_EXPECTED_UID`、`SECRET_EXPECTED_GID` 明確設定；檔案型秘密模式下未設定或無效即安全拒絕。主機來源檔與容器掛載檔分開驗證；不假設主機與容器帳號名稱或 UID/GID 相同；不假設 Compose 會替檔案型秘密設定 uid、gid、mode。
- **夥伴的權限風險**：若夥伴擁有主機管理員或完整 Docker 權限，技術上可能讀取執行時秘密。部署文件須明說，不宣稱 Docker secrets 對其保密。
- **資料庫權限**：見 `docs/db-least-privilege.md`。Bot 執行期使用 `jukebox101_app`（SELECT、INSERT、UPDATE），不含 DELETE、DDL、GRANT；Migration 使用獨立維護帳號。
- **維持不變**：Gateway-only、YouTube-only、外部 MySQL 預設、單一副本、未核准項目不啟用。
