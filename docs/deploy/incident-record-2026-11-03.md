# 2026-11-03 啟用過程的問題紀錄與處理（#18、#20、#21 上線後）

本文件記錄 2026-11-03 在 VM 啟用自動審核、正式 `/exchange`、`/daily` 時實際遇到的問題、原因、處理與仍未解決的事項。不含秘密、專案代碼或使用者識別資料。程式與測試的細節見各 PR；VM 步驟見 `vm-enable-procedure-2026-11-03.md`。Agent 不連線 VM、正式資料庫與 Discord，下列正式環境操作均由 Owner 執行。

## 1. 版本衝突凍結了整個發獎（PR #29，已合併部署）

- **現象**：三筆案件在 `/history` 顯示「版本衝突待處理」，沒有人能領到 Nickel。
- **原因**：
  1. Owner 先手動「確認為新的錄音版本」，影片仍是待驗證；自動審核開啟後，同一支影片被自動核准，系統又蓋上自己的版本 → 同一影片兩個矛盾版本 → 凍結為衝突。這是缺陷：自動版本確認沒有檢查影片是否已有 Owner 確認的版本。
  2. 依保守規則，**未知版本的衝突會連帶凍結所有尚未發放的案件**，且 `conflict_frozen` 是黏性的，之後才進來的投稿也會被凍結。
- **修正（PR #29）**：自動版本確認遇到已確認版本或已凍結衝突時不再蓋章（Owner 優先）；新增 Owner 專用 `owner_cli conflict-resolve preview/write`（驗證碼綁定、決定鍵冪等）：保留指定的 Owner 證據、把矛盾版本併為同一個、解凍僅因此衝突而被連帶凍結的案件。
- **正式環境處理**：`preview` 確認證據與版本號 → `write`（帶驗證碼與版本號）→ `/history` 三筆恢復；以 `owner_cli settle`（只對指名案件短暫開啟發獎開關）發出該兩筆，健康檢查 `ready`、無 `SETTLEMENT_*`。
- **預防**：自動審核開啟期間，不要對仍在待驗證的投稿手動確認版本；需要時先把四個自動審核開關改回 off。

## 2. `owner_cli` 在正式容器的連線問題（尚未修，PR 待開）

- `owner_cli` 只認 `DB_PASSWORD`，不認容器使用的 `DB_PASSWORD_FILE`；也沒有帶 `DB_SSLROOTCERT`，`verify-full` 因找不到 CA 而失敗（只回 `OperationalError`）。
- **暫時繞法**（密碼不顯示、不落地）：
  `docker exec jukebox101-bot-1 sh -c 'PGSSLROOTCERT="$DB_SSLROOTCERT" DB_PASSWORD="$(cat "$DB_PASSWORD_FILE")" python -m bot.owner_cli <子命令>'`
- 此繞法適用於 `exchange-stuck`、`conflict-resolve`、`settle`、`settlement-switch`。
- **待辦**：讓 `owner_cli` 直接支援 `DB_PASSWORD_FILE`、`DB_SSLROOTCERT`、`DB_SSLMODE`，並補測試。

## 3. Discord 指令出現兩套、Windows 桌面版沒有 `hour`

- **原因**：Owner 伺服器上留有舊的「伺服器專屬」使用者指令（`daily` 只有 `mode`），與全域更新後的指令並存；全域 `apply` 不會覆蓋伺服器專屬指令。
- **處理**：`command_sync fetch --target owner-guild` 證實後，`apply --target owner-guild` 以本地只含 `owner` 的指令集覆蓋該伺服器；之後只剩一份使用者指令且 `/daily` 有 `hour`，`owner` 補上 `duration`。
- **注意**：更新全域指令後，也要檢查 Owner 伺服器是否留有舊的伺服器專屬副本。

## 4. 指令與卡片「慢半拍」（原因確認，尚未處理）

- **量測**：VM 在 GCP `us-central1-c`，資料庫為 Supabase `eu-central-1` 連線池；TCP 連線時間約 0.12 秒（單趟往返約 120 毫秒）。容器 CPU 約 0.1%、記憶體約 10%，日誌無逾時。
- **程式面**（唯讀調查，未獨立壓測）：每個資料庫操作新建連線（TCP＋TLS＋驗證，約 5 到 6 趟）；每個交易取全域鎖前還有 3 趟起手式；Owner 按鈕確認約開 8 到 12 條連線；審核與發獎每次讀出全部事件重算並逐筆 UPDATE（持鎖時間隨事件數線性成長）。
- **選項**（未決）：把 VM 搬到歐洲區域（效果最大，可能離開 GCP 免費方案）；在美國另建 Supabase 專案並遷移（風險較高）；改程式減少來回（連線重用、只更新有變的事件、純讀取不拿寫入鎖）。
- 這不是故障，沒有資料損壞；建議之後有決定再處理。

## 8. 補充：每日提醒也佔用當天的名額（設計後果，非故障）

- 每人每個台北日只有一個每日任務，**提醒（餘額不足、無候選歌曲）也算這一個任務**。當天已經收過提醒，即使之後有 Nickel 或新歌，也要到**隔天**才會再送。
- 驗收時的影響：2026-11-03 13:01 收到無候選提醒的帳號，同日 14:00 沒有收到推薦，這是預期行為。要驗證「成功的每日推薦」，請用當天還沒收過任何每日訊息的帳號，或等隔天。
- 若日後要改成「提醒不佔名額」，屬於產品規則變更，需另行核定。

## 9. 每日超過 10 首的投稿永遠沒有時長（Owner 於 2026-11-03 確認 #31 屬此情況）

- **現象**：Owner 清單的 #31 卡片顯示「已知時長：尚無」，只剩「補時長」，系統沒有自動取得時長。
- **原因（程式碼確認）**：`bot/auto_pipeline.py` 的 `_review_step` 對「同一人、同一個台北日已超過每日上限（`MAX_REWARDED_SUBMISSIONS_PER_DAY = 10`）」的第 11 首起直接跳過，**不向 YouTube 查詢**（目的是不替超額投稿花配額）。判斷依據是投稿**當天**同人更早的投稿數（`bot/database/auto_review_store.py` 的 `read_subject`），這個數字固定不變，所以之後每次掃描都會跳過，案件永遠停在待驗證、沒有時長。
- **性質**：不是故障，是「超額不查詢」規則與「Owner 要審核這些案件」之間的缺口：Owner 看得到這些案件，卻拿不到時長，只能手動輸入。
- **其他也會造成「尚無時長」的情況**（仍屬預期）：影片是直播、首播或還在處理中；API 暫時失敗或配額用完（暫停 30 分鐘再試）；影片已刪除或未公開（標為「無法取得影片資料」）。
- **關聯的文字問題（已修，尚未提交）**：改版後卡片的狀態行寫成「尚無完整影片時長，請先補時長」，讓 Owner 以為自動取得被拿掉。已改回：「系統正在自動取得影片時長；也可以先補時長」、「系統無法取得影片資料…」、「官方時長資料已過期，系統會自動重新驗證…」。自動取得時長的程式本身沒有被改動。
- **未決（等 Owner 核定）**：讓 Owner 在「按『是，發獎』或開詳情」當下就近向 YouTube 查該影片時長（每案最多 1 個配額單位），失敗才留「補時長」；涵蓋超額案件。選項 A（建議）／B（取消超額不查）／C（兩者），見交接文件。

## 10. 全域鎖與延遲造成的 `LockNotAvailable`（部分緩解，架構未決）

- **日誌**：`ERROR bot.services: Database operation failed: LockNotAvailable`、`ERROR bot.daily_runner: Daily sweep failed: LockNotAvailable`。
- **原因**：寫入交易在 `submission_transaction` 內以 `SELECT ... FROM jb2_control FOR UPDATE` 取得**全域**序列化鎖（`LOCK_WAIT = 2s`，連線 `lock_timeout` 5 秒、`statement_timeout` 10 秒）；加上跨區延遲（約 120 毫秒往返）使持鎖時間拉長，並發時後面的請求等不到鎖。每個操作新建連線；審核與發獎每次讀出全部事件重算並逐筆更新。
- **量測（模擬，拋棄式 PostgreSQL 加網路延遲，非正式環境）**：120 毫秒往返下 `/share` 約 26 秒、`/exchange` 約 8 秒；12 人同時使用約 96% 的投稿失敗。由 `scripts/dev/stress_simulation.py` 產生（PR #35）。
- **已做的緩解**：PR #34「只擋自己的塞車規則」（未知版本的待處理與衝突只凍結同一投稿者）；PR #37 比對期間容忍 30 筆同時投稿，不再大量退回人工。
- **未決**：縮短持鎖、改為每人／每案件鎖、重新設計，或搬 VM 到歐洲區域。Owner 已表示暫不搬 VM、不做私訊 Bot。目前**沒有 VM**（見交接文件）。

## 12. 部署與 CI 的踩坑

- **兩道發獎鎖必須一致**：資料庫開關與 `JUKEBOX_AUTO_SETTLEMENT` 兩者不一致時，健康檢查與 CD 會失敗；合併即觸發 CD，需依 `stage-b-enable-rollback.md`／`vm-enable-procedure-2026-11-03.md` 的順序操作（PR #32）。
- **`bot.env` 修改**需要一個新的 commit 才會觸發 CD。
- **CI 測試數量下限**：離線與 PostgreSQL 各有下限，改測試數量後要同步調整（PR #38 把 PostgreSQL 下限設為 253；PR #39 為離線 2780、PostgreSQL 258）。
- **偶發失敗**：`613` 洩漏掃描測試曾比對到隨機十六進位字串；PR #37 已加上前後非數字的邊界（`tests/test_postgres_auto_version_confirm.py` 第 351 行）。

## 13. 本機開發工具的陷阱（給下一位接手者）

- **用 Bash 工具的 heredoc 或 `python -` 改檔時，字串裡的 `\n`（反斜線 n）會被當成真正的換行寫進檔案**，造成「unterminated string」之類的語法錯誤。改含逸出字元的程式碼，請改用 Edit 工具，不要用 Python 腳本替換。
- 專案檔案多為 CRLF，用 Python 做精確字串替換前要先判斷換行字元，否則比對不到。
- 測試一律用 `bash scripts/dev/run-linux-tests.sh offline|postgres [pytest 參數]`；本機 `.venv` 缺 `psycopg`，直接跑 pytest 會在收集階段失敗。
- 該腳本的 `-q` 已內建，再多加 `-q` 會讓輸出沒有「N passed」總結行；要看總數請不要再加 `-q`。
