# 階段 C：正式開放 `/daily` 的啟用與回滾清單

狀態：**草案，實作與測試進行中、尚未部署、尚未啟用**。`JUKEBOX_FORMAL_DAILY` 預設 off；合併程式碼本身不會開放 `/daily`，也不會開始每日派送。本文件所有指令都在 VM 上以 `sudo docker exec jukebox101-bot-1 python -m bot.…` 執行，文中不放任何秘密。標「待確認」的項目是尚未驗證的事實或尚未定案的規則。

背景：[測試與部署計畫 §7.1、§7.3](../auto-review-test-deploy-plan.md)、[階段 B 啟用清單](stage-b-enable-rollback.md)、[持續部署](continuous-deployment.md)。對應 issue #21。

## 0. 這份文件要你決定什麼

要決定的有兩件事，而且順序固定：

1. **何時對正式資料庫套用 migration 0005（新增兩張資料表）。** 這是受保護的資料庫變更，需要 Owner 另行明確授權；系統不會自動套用。沒有它，`/daily` 開關開了也不會運作（健康檢查會擋下）。
2. **何時把 `/daily` 從「尚未開放」改成「正式開放」。** 開放後，訂閱的使用者每天在自己選的整點（台北時間）收到一則私訊推薦，每則扣 1 Nickel。

以下是已核定的規則（不是本文件新定的）：

| 情況 | 系統怎麼做 | 使用者看到什麼 |
|---|---|---|
| `/daily on` | 訂閱，時間預設 20 點（台北時間） | 確認訊息，說明時間為台北時間 |
| `/daily on 9` | 訂閱，每天 9 點（可填 0–23 的整點） | 同上，顯示 9 點 |
| 時間填錯（`20:30`、`24`、文字） | **不改原設定**，說明可用範圍 0–23 | 錯誤說明 |
| `/daily off` | 停止之後的派送，歷史保留，時間設定也保留 | 確認訊息 |
| 今天還沒派送時改時間 | 新時間今天就生效 | — |
| 今天已派送後改時間 | 今天不再送，明天起用新時間 | — |
| 服務停機錯過時段 | 恢復後**同一天**補送一次；跨日不補 | 較晚收到 |
| 正常派送 | 預約時扣 1 點、私訊 1 次；沿用階段 B 的選曲與退款規則 | 私訊含連結與推薦者半遮蔽名稱 |
| 私訊明確沒送出 | 退 1 點；**當天不重試**，明天照常 | 無（私訊本來就沒送到） |
| 私訊結果不明 | 不退點、不重送，列入 `exchange-stuck` | 無；隔天因有未了案件而不派送 |
| 點數不足 | 不扣點，私訊「Nickel不夠了…快去分享歌曲，賺點Nickel！」；每天最多 1 則；連續 3 天沒補點後靜默 | 該則提醒 |
| 沒有可推薦的歌 | 不扣點，私訊說明；同樣每天最多 1 則、連續 3 天後靜默 | 該則說明（確切文案待 Owner 確認） |
| 補點之後 | 當天不補送；隔天正常派送；再次不足時重新計算 3 天 | — |

取捨說明：

- 「當天私訊失敗不重試」代價是使用者可能少收一次，好處是不會在對方封鎖私訊時每次掃描都打 Discord、也不會因重試造成重複送出。
- 「結果不明不退點」延續階段 B：寧可使用者暫時少一點，也不送兩次；這類案件 Owner 要從卡住清單看到並跟進。
- 「連續 3 天靜默」避免對長期不上線的人每天發訊息；代價是他們補點後前幾天看不到提示。

## 2. 啟用順序

1. **部署新映像，開關維持 off。** 推 commit 讓 CD 部署（`bot.env` 只在重建容器時生效，不要手動重建）。驗證：
   - `sudo docker exec jukebox101-bot-1 python -m bot.healthcheck` 顯示 `"result": "ready"`。
   - 在 Discord 執行 `/daily on`，仍回「尚未開放」，不寫入任何偏好。
2. **備份資料庫。**（方式依 [owner-secrets](owner-secrets.md) 與管理者既有流程：**待確認**）
3. **檢視 migration 計畫（唯讀）。** `sudo docker exec jukebox101-bot-1 python -m bot.migrate plan`，預期只列出 0005 為待套用，並顯示其摘要值（digest）。
4. **取得 Owner 明確授權後套用。** 依 [v7 部署文件](v7-postgresql-deployment.md) 的 migrate 流程執行 `apply --apply`（需要 migrator 角色，不在 Bot 容器內執行時的指令以該文件為準：**待確認**）。套用後：
   - 再跑一次 `plan`，預期無待套用項目。
   - 唯讀檢查兩張新表存在、應用角色對它們沒有 DELETE 權限（可用 `readonly` 角色查詢；SQL 由實作者在 PR 附上：**待確認**）。
5. **確認卡住清單與帳本一致。** `sudo docker exec jukebox101-bot-1 python -m bot.owner_cli exchange-stuck` 預期無案件（唯讀）；帳本完整性檢查須為 PASS（做法同階段 B 第 2 節第 3 步）。
6. **同步 Discord 指令**（讓 `hour` 欄位出現）。`python -m bot.command_sync preview` 檢查差異，確認只多一個 `daily` 的 `hour` 參數，再由 Owner 決定是否 `apply`。
7. **開開關。** 在 root 擁有的 `/etc/jukebox101/bot.env` 設 `JUKEBOX_FORMAL_DAILY=on`，推新 commit 重建容器。`JUKEBOX_NICKEL_CLAIM` 維持 `off`。
8. **驗證健康。** `python -m bot.healthcheck` 仍為 `ready`；若 migration 0005 尚未套用卻開了開關，預期健康檢查**不是** `ready`（具體錯誤代碼：**待確認**）。
9. **跑第 3 節的真實 Discord 驗收。** 通過前不對一般使用者宣布開放；驗收帳號可先把自己的時間設成「下一個整點」測試。

## 3. 真實 Discord 驗收清單（Manual Pending，尚未執行）

自動測試用拋棄式 PostgreSQL 與腳本化的假私訊，不能證明 Discord 真實行為（半遮蔽名稱的實際顯示、私訊是否真的不提及任何人、真實封鎖私訊的錯誤型態）。以下需人工逐項確認並記錄；每項做完用 `/balance` 與 `exchange-stuck` 核對。

| # | 動作 | 預期 | 結果 |
|---|---|---|---|
| 1 | B（有 1 Nickel）執行 `/daily on`，不填時間 | 回覆顯示 20 點（台北時間）；不立刻扣點 | 待測 |
| 2 | B 執行 `/daily on 25`、`/daily on` 搭配文字（Discord 前端會擋；若能送出） | 不改原設定，說明可用範圍 | 待測 |
| 3 | B 把時間設成下一個整點，等時間到 | 該整點後收到 1 則私訊：含 YouTube 連結與推薦者半遮蔽名稱；`/balance` 少 1；頻道內無公開訊息 | 待測 |
| 4 | 檢查那則私訊 | 名稱保留頭尾、中間為 `*`；無完整名稱、無 Discord ID、無可點擊的提及（`@` 開頭的名稱也不會 ping） | 待測 |
| 5 | 同一天再等一個整點或重啟容器（`sudo docker restart jukebox101-bot-1`） | 不會再收到第二則、不再扣點 | 待測 |
| 6 | 派送後當天把時間改到更晚的整點 | 今天不再送；隔天在新時間送 | 待測 |
| 7 | B 餘額為 0 時到點 | 收到「Nickel不夠了…快去分享歌曲，賺點Nickel！」；`/balance` 不變；同日不重複 | 待測 |
| 8 | 連續 3 天餘額為 0 | 第 1–3 天各 1 則，第 4 天起不再發；補點後當天不補送、隔天正常派送 | 待測（需 4 天以上，可由 Owner 決定是否以測試資料縮短） |
| 9 | 歌池沒有可推薦的歌（B 已收過全部他人歌曲）且有點數 | 收到無候選說明；點數不變 | 待測 |
| 10 | B 關閉「允許來自伺服器成員的私訊」後到點 | 若 Discord 明確回報未送出：退 1 點；同日不重試；明天照常。若結果不明則依第 5 節處理 | 待測 |
| 11 | B 執行 `/daily off` | 之後不再派送；歷史（`/history`）仍在；再次 `/daily on` 沿用原時間 | 待測 |
| 12 | 兩個帳號同一整點到點，其中一個封鎖私訊 | 另一個照常收到，不被拖慢 | 待測 |

結果不明（逾時／斷線）無法在真實 Discord 上安全重現，**不列入人工驗收**；它由自動測試以腳本化私訊結果覆蓋。

## 4. 監看與卡住案件

- 派送的卡住案件與階段 B 相同，用 `sudo docker exec jukebox101-bot-1 python -m bot.owner_cli exchange-stuck` 唯讀查看（原因代碼與跟進原則見[階段 B 文件第 4 節](stage-b-enable-rollback.md)）。每日派送產生的預約同樣會出現在這份清單。
- 提醒類私訊（點數不足、無候選）失敗不會扣點，也不進卡住清單；它們只記錄在 `daily_notices`（每人每日一列）。是否需要 Owner 專用的檢視指令：**待確認**，本期若無，管理者以唯讀 SQL 查。
- 不得直接改資料庫餘額、帳本或 `daily_dispatches`／`daily_notices`。

## 5. 回滾（由輕到重）

| 狀況 | 做法 | 會發生什麼 |
|---|---|---|
| 懷疑每日派送有問題 | `/etc/jukebox101/bot.env` 設 `JUKEBOX_FORMAL_DAILY=off`，推新 commit 重建 | 立即停止新的派送與提醒；`/daily` 回「尚未開放」。**已扣的點、已送出的私訊不收回**；使用者的訂閱與時間設定保留，下次開啟後沿用 |
| 單一使用者問題 | 請該使用者 `/daily off`；或 Owner 經工程人員在核准下處理 | 之後不再派送給他 |
| 回滾後使用者說被扣點 | 先跑 `exchange-stuck` 與帳本對帳 | 已保留案件依階段 B 第 4 節處理；不得直接改資料庫 |
| 新映像不健康 | 主機腳本自動換回前一個映像，回報 `rolled_back` | 看 `docker logs`；`rolled_back` 路徑在真實主機尚未驗證過 |
| 要回到階段 C 之前的映像 | 先把開關設 off，並確認 `exchange-stuck` 為空、最近沒有進行中的派送 | 舊映像看不到新表，但 migration 0005 只**新增**資料表，不改既有表，舊映像仍可正常運作（`users.daily_enabled` 與 `daily_dispatches` 原樣保留）。舊映像不認得每日派送規則，所以必須先 off |
| 要移除 migration 0005 | **不提供。** 不刪表、不降級 | 新表留在資料庫不影響舊程式；若有特殊需求須由 Owner 另行核准 |

單向門提醒：migration 0005 套用後，資料庫就留有新表與資料（偏好、提醒紀錄、派送紀錄）；回滾映像與關開關都不會刪除它們。這是刻意的：保留歷史、避免破壞性 DDL。

## 6. 已知限制與待確認

- 真實 Discord 驗收（第 3 節）尚未執行；半遮蔽名稱的實際顯示與 allowed_mentions 行為尚未在真實 Discord 驗證。
- 「新時間已經過了的整點」（例如現在 15 點、當天還沒派送，把時間改成 9 點）會不會當天立刻補送：規則文字（今天還沒派送，新時間今天就生效；停機錯過會當天補送）傾向「立刻送」，測試尚未鎖定，**待 Owner 確認**。
- 一個字的名稱顯示為單一 `*`（避免完整洩漏），與「1–2 字名稱只留第一字」的字面有出入，**待 Owner 確認**。
- 無候選歌曲提醒的確切文案**待 Owner 確認**（目前由具名常數表示，可只改常數與測試）。
- 受控 compose 放寬（第 1 節，已實作待 CI 確認）、migration 套用方式（第 2 節第 4 步）、備份方式（第 2 節第 2 步）、健康檢查對「缺 migration」的錯誤代碼：**待確認**。
- 派送由 Bot 內的背景排程執行，掃描頻率與在單一實例下的行為由實作者說明；多實例部署不在本期範圍。
