# JukeBox101 Docker 部署：需求輸入（供手動執行 /to-spec 使用）

狀態：需求輸入，尚未經 /to-spec 或 /to-tickets 產出規格與工作票。在規格與工作票完成前，不修改程式、Dockerfile、Compose 或部署文件。

## 1. 目標

- 以 Docker Compose 部署到 Linux amd64 主機。
- 採 Gateway-only：Bot 主動連線 Discord；不開公開 HTTP Interactions 入口；不要求反向代理、網域或 HTTPS。
- 預設使用外部 MySQL 8.0.16+；另提供選用的同機 MySQL Compose profile。

## 2. 角色與權限邊界

- 擁有者（Owner）：建立、保管、配置及輪替所有秘密（資料庫密碼、Discord Bot Token）。
- 夥伴（Partner）：在自己管理的主機上，以 Docker Compose 部署精簡交付包。夥伴擁有該主機的管理權限與 Docker 權限，不需要為了本專案受限制。
- 交付方式：交付包直接交給夥伴。交付包、映像與 Compose 檔不含真實秘密。
- 秘密交付：夥伴完成 Docker 與程式部署準備後，由 Owner 透過獨立安全管道配置秘密，不經由交付包或聊天傳送。
- 權限承認：夥伴若擁有主機管理員或完整 Docker 權限，技術上可能讀取容器使用的秘密。文件不得宣稱 Docker secrets 能對主機管理員保密，也不是自動加密保管庫。

## 3. 秘密處理（必須）

- 交付包、映像、Compose 檔不含真實秘密。
- 夥伴先完成 Docker 與程式部署準備；之後 Owner 透過獨立安全管道，在部署主機上一次性配置秘密檔案。
- 正常部署與更新沿用已配置的秘密檔案，不需夥伴或 Owner 重新提供。
- 優先使用 Compose secrets 掛載檔案。程式必須明確支援從秘密檔案讀取；不假設 `_FILE` 環境變數會自動生效。
  - 現況確認：`bot/config.py` 的 `required_environment_value` 與 `DB_PASSWORD`、`DISCORD_BOT_TOKEN` 只讀環境變數，沒有檔案讀取。
  - 需新增明確的檔案讀取支援，並定義優先順序、同時設定時的拒絕規則與權限檢查。
- 缺少必要秘密時安全停止；不使用預設密碼；錯誤訊息不輸出秘密值。
- 「容器已建立」不等於「Bot 已可用」。健康檢查與文件必須區分：容器存活、設定載入成功、Discord 連線成功。
- 秘密不得注入建置階段（不使用 Dockerfile ARG/ENV，本次不採用 build secrets）、不寫入交付包、日誌或診斷報告。
- 資料庫帳號：
  - Bot 使用專用、最小權限帳號，只授予應用程式所需權限。
  - 不提供資料庫管理員或 root 密碼給部署環境。
  - Migration 使用另外管理的帳號，不放入 Bot 容器。
- 秘密持久保存：秘密檔案位於部署主機上、專案目錄之外，權限 0600（或等效限制），由 Owner 配置。
- 秘密輪替：Owner 更新秘密檔案後，需重建或重啟容器才會生效；文件需說明步驟與回滾。
- 缺少秘密檔案時，Compose 或程式必須停止，不得以空值啟動。

## 4. 文件分工（必須分開）

- 夥伴部署與更新文件：Docker 前置需求、部署步驟、啟動、健康檢查（說明實際驗證範圍）、日誌、停止、更新、回滾、資料備份。文件不要求夥伴填寫真實秘密，但說明秘密檔案已由 Owner 配置時如何沿用。
- 擁有者秘密配置與輪替文件：建立 Bot 專用資料庫帳號與 Migration 帳號、建立秘密檔案、配置位置與權限、首次交付前的檢查、輪替步驟與生效方式、洩漏時的處置。
- 既有 `deploy/RUNBOOK.md` 與兩個模板：採方案 A，保留並標示為「未採用的 HTTP 候選方案」，不搬移、不覆寫。新 Gateway 手冊另寫。

## 5. 功能範圍

- Gateway 路徑是本次部署的完整入口：包含 `/share`、`/balance`、`/history`、`/daily`、`/exchange` 與 `/owner` 群組。
- HTTP 路徑不納入本次部署，但程式與安全檢查保留，不刪除、不重構、不靜默停用。
- `/exchange` 等正式功能的開關維持既有 fail-closed 行為（`JUKEBOX_FORMAL_EXCHANGE` 預設關閉）。

## 6. 回覆文案

- 統一使用 Nickel（不使用「點數」作為面向使用者的詞）。
- 既有逐字核准台詞保持原樣（`bot/share_replies.py` 的 5 句）。
- 新文案待擁有者確認後套用，不阻擋容器、安全、政策與交付工作。

## 7. Python 與測試

- 測試與執行使用 Python 3.12（可用路徑：`/home/gaston/.local/bin/python3.12`，3.12.15）。
- `/usr/bin/python3`（3.14.4）不屬於本專案範圍，不得用於驗收。

## 8. Docker 與驗證要求

- 映像：精簡、支援 linux/amd64、非 root 執行、不含測試或編譯工具。
- 依賴：可重現的版本鎖定（`dependency-versions.txt` 為既有版本清單）。
- 信號：正確處理 SIGTERM、連線關閉與工作清理。
- 健康檢查：不得反覆呼叫 Discord API；說明實際驗證範圍。
- 資源限制：Compose 的 CPU 與記憶體限制必須確認在選定模式實際生效；為作業系統及同機 MySQL 留足空間。
- 離線驗證：使用明確假值與隔離設定；容器不得連線正式 Discord 或正式 MySQL。不得修改入口以繞過 fail-closed 或偽裝健康。
- 驗證分類：區分「離線容器驗證通過」與「正式 Bot 連線可用」。正式連線需另行授權。
- 驗證項目：建置、非 root、必要檔案權限、SIGTERM 關閉、Compose 資源限制、映像與各層機敏掃描、交付包解壓後掃描、SHA-256。

## 9. 磁碟與環境

- C 槽剩餘約 11 GiB（96% 使用）。建置前重新確認 Docker Desktop 儲存位置與可用空間。
- 不執行全域 prune；不清理既有容器、映像、volume、WSL 虛擬磁碟或使用者檔案。
- Docker 指令在目前 shell 無 docker 群組權限時，透過 `wsl.exe -d Ubuntu --` 新工作階段執行；不放寬 socket 權限。

## 10. 交付包

- 包含：實際必要程式、Dockerfile、Compose、依賴鎖定、假值設定範例、部署文件、必要 SQL 資源與授權資訊。
- 不包含：`.env`、`.local/`、`.git/`、私人驗收證據、真實憑證、資料庫 dump 或 volume、虛擬環境、快取與日誌。
- 不依賴 `.gitignore`；使用獨立的 Docker 排除規則與交付允許清單。

## 11. 未決事項（需 Owner 決定）

- 秘密安全管道：Owner 用哪種方式把秘密配置到夥伴主機（例如加密傳輸、雙方共用的一次性通道），不經交付包或聊天。
- 秘密檔案在夥伴主機上的確切路徑與擁有者權限（目前建議：專案目錄外、權限 0600）。
- 外部 MySQL 與同機 MySQL 的備份與回滾責任分工。
- `deploy/` 既有 HTTP 文件的標示文字（方案 A 已決定保留）。
