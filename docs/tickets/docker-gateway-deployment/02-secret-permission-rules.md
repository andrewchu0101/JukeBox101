# 02：秘密檔案權限的判定規則（主機來源檔與容器內掛載檔分開判定）

**What to build:** 一個純判定模組，輸入為檔案的擁有者、群組與權限位元，以及執行程序的身分，輸出為「通過」、「警告」或「拒絕」與原因代碼。它不讀取檔案內容，不呼叫 Docker，不輸出秘密。

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent（判定嚴格度的建議值需 Owner 確認，見下方）

**File owner:** `bot/secret_file_policy.py`（新）、`tests/test_secret_file_policy.py`（新）

## 判定規則（建議值，需 Owner 確認）

本規則分兩個場景，因為 Compose 掛載會沿用主機檔案的擁有者與權限，但主機與容器看到的身分不同。

### 場景 A：部署主機來源檔（夥伴或 Owner 的部署前檢查）

| 條件 | 判定 | 原因代碼 |
|---|---|---|
| 其他人（other）有任何讀、寫、執行位元 | **拒絕** | OTHER_ACCESS |
| 群組有寫入位元 | **拒絕** | GROUP_WRITABLE |
| 擁有者不是預期的部署帳號 | **拒絕** | UNEXPECTED_OWNER |
| 群組有讀取位元，且群組不是預先指定的秘密群組 | **拒絕**（部署前檢查；輸出不含秘密的修復說明，見下） | GROUP_READ_UNDEDICATED |
| 權限為 0400（已核准的唯一模式） | **通過** | — |
| 權限為 0600、0440 或其他值 | **拒絕**（NOT_SANCTIONED_MODE；2026-10-29 統一為 0400） | — |

**部署前檢查的修復說明（不含秘密）：** 只列出目前的擁有者、群組與權限位元（數字與符號），以及預期的擁有者與群組，並給出修復指令範本（例如 `chown <預期擁有者>:<預期群組>` 與 `chmod 0440`）。不輸出檔案內容、長度或雜湊。

**可設定項目：** 預期擁有者與預期秘密群組必須可由部署者設定（不寫死於程式），預設值為空；未設定時部署前檢查失敗並提示設定，不以預設值通過。

### 場景 B：容器內掛載檔（程式啟動時檢查）

| 條件 | 判定 | 原因代碼 |
|---|---|---|
| 程序的有效使用者為 root（uid 0） | **拒絕**（容器必須非 root） | RUNS_AS_ROOT |
| 程序無讀取權限 | **拒絕**（不輸出路徑以外的細節） | NOT_READABLE |
| 其他人有任何位元 | **拒絕** | OTHER_ACCESS |
| 檔案為空或只有空白 | **拒絕** | EMPTY |
| 群組位元存在，且程序屬於該群組 | **通過**（這是預期的 0440 用法） | — |

## 重要：不要把 Compose 掛載的權限差異一律判成洩漏

- 0440 且群組為容器程序群組：**通過**，這是讓非 root 容器讀取的正常設定。
- 主機來源檔為 0600 且擁有者不是容器使用者：場景 B 會判為「無法讀取」，這是**可讀性問題**，不是洩漏。文件要說明修正方式，而不是放寬權限。
- **不假設 Compose 能替檔案型秘密設定 uid、gid、mode。** 容器內的實際擁有者、群組與權限，一律以容器內讀取的結果為準；本票的判定只接受實際 UID／GID 與權限位元作為輸入。Compose 行為由工作票 10、11 以實測確認，記錄 Compose 版本與結果。

## TDD 驗證

- 紅：其他人有讀取位元 → 場景 A 與 B 皆拒絕。
- 紅：0440 且群組為容器群組 → 場景 B 通過；場景 A 通過。
- 紅：0440 且群組不是指定群組 → 場景 A 警告，不拒絕。
- 紅：程序為 uid 0 → 場景 B 拒絕，即使權限為 0600。
- 紅：無讀取權限 → 場景 B 拒絕，原因代碼不含路徑以外的敏感內容。
- 紅：空檔案 → 場景 B 拒絕。

**Acceptance criteria:**
- [ ] 兩個場景的判定以純函式實作，輸入是模擬的檔案屬性，不需要真實檔案系統。
- [ ] 每個判定都有可追溯的原因代碼。
- [ ] 0440 搭配容器群組的情境一定通過，不被誤判。
- [ ] 判定結果不含秘密值。
- [ ] 離線測試以 Python 3.12 執行通過，並分開列出通過、失敗、略過數量。
